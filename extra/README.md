# OSreboot: компьютер сам восстанавливает стёртую систему через интернет

> **Аннотация.** Компьютер с уничтоженной системой на диске обычно не
> поднимется без человека с загрузочной флешкой. В дата-центрах эту задачу
> решают контроллер удалённого управления (BMC) и сервер сетевой загрузки в
> той же сети, а производители ПК — закрытые механизмы восстановления в
> прошивке. В OSreboot ноутбук без BMC восстанавливает стёртые разделы сам,
> через интернет. Прошивка запускает iPXE с раздела, который затирание не
> трогает, iPXE по HTTPS загружает с VPS среду восстановления, а она скачивает
> образы разделов, проверяет SHA-256, записывает их и перезагружает машину.
> Сервер измеряет простой по сигналам heartbeat раз в секунду и показывает
> этапы восстановления в реальном времени. На ноутбуке весь простой, от
> команды затирания до первого heartbeat восстановленной системы, занял 164 и
> 166 с в двух прогонах. Больше половины этого времени ушло на две загрузки
> машины, треть — на скачивание, которое упиралось в 100-мегабитное подключение
> ноутбука. Обзор существующих решений показал, что ни одно из них не
> сочетает работу без BMC, загрузку через интернет, открытый стек для Linux и
> внешний замер простоя.

## 1. Введение

Система на диске может погибнуть по многим причинам: ошибка администратора
(`rm -rf /`, `dd` не на тот диск), сбой обновления, шифровальщик, повреждение
файловой системы. Итог один: компьютер не загружается, и чинить его приходит
человек с загрузочной флешкой. Если компьютер стоит далеко — например,
домашний сервер, пока владелец в отъезде, — простой длится часы или дни.

В дата-центре эта задача решена давно. У сервера есть BMC (iDRAC, iLO, IPMI)
— отдельный компьютер на плате, через который администратор включает питание,
видит экран и подключает образ, а системы вроде MAAS и Ironic
переустанавливают ОС по сети [1, 2]. Им нужны BMC и свой
сервер сетевой загрузки в той же сети. У обычного ПК и ноутбука нет ни того,
ни другого.

Производители ПК встроили восстановление по сети в прошивку и ОС
[3, 4, 5, 6, 7]. Но эти
механизмы закрыты и восстанавливают только «свою» систему — Windows или
macOS, — как правило, со своих серверов.

Цель работы — показать, что обычный компьютер без BMC и без помощника в
локальной сети может сам восстановить уничтоженную систему через интернет
открытыми средствами, и измерить, сколько при этом длится простой. Требования
к решению:

- **без BMC и без второго компьютера рядом:** всё нужное для восстановления
  приходит с VPS через интернет;
- **без человека:** после команды «уничтожить систему» машина поднимается
  сама;
- **безопасно:** пишутся только два тестовых раздела, остальной диск не
  трогается, а в публично доступных образах нет секретов;
- **измеримо:** простой и время каждого этапа фиксирует внешний сервер, а не
  сама машина.

Вклад работы:

1. цепочка восстановления, проверенная на ноутбуке без BMC: прошивка UEFI →
   iPXE по HTTPS → среда восстановления в памяти → проверка и запись образов →
   загрузка восстановленной системы;
2. сервер, который измеряет простой по сигналам heartbeat и показывает этапы
   восстановления в реальном времени;
3. обзор готовых решений и исследований (раздел 2);
4. первые замеры на ноутбуке и в виртуальной машине (раздел 4).

## 2. Существующие решения и исследования

Обзор охватывает готовые решения — промышленные и открытые — и исследования
о восстановлении систем. Поиск шёл в октябре 2026 года по документации
производителей и проектов и по научным публикациям; ниже разобраны решения,
ближайшие к задаче. Ключевые утверждения сверены по самим страницам
источников. Но «не нашли» не значит «не существует»: поиск не исчерпывающий.

### 2.1. Восстановление в прошивке и ОС персональных компьютеров

Производители ПК и ОС давно встроили восстановление по сети в прошивку или в
среду восстановления на диске:

- **Dell SupportAssist OS Recovery и BIOSConnect** [3]. После нескольких
  неудачных загрузок подряд (порог от 1 до 3, по умолчанию 2) восстановление
  запускается само. Сначала пробуется раздел восстановления на диске, затем
  BIOSConnect скачивает служебную ОС размером 1–2 ГБ с серверов Dell по HTTPS
  в RAM-диск. Восстанавливается заводская Windows, с Linux механизм не
  работает. Полное стирание диска переживает только вариант BIOSConnect,
  целиком встроенный в прошивку.
- **HP Sure Recover** [4]. Переустанавливает Windows из образа WIM с сервера
  HP, со своего HTTP- или FTP-сервера компании, с локального раздела или из
  отдельной микросхемы (Embedded Reimaging). Свой образ описывается манифестом
  с SHA-256 и подписывается, а ключи для проверки хранятся в контроллере
  безопасности HP. Запускает пользователь, когда Windows не загружается, или
  администратор: по расписанию либо после N перезагрузок. Работает только на
  бизнес-ПК HP.
- **Lenovo Cloud bare metal recovery** [5]. На отдельных моделях ThinkPad
  пункт «Reinstall Windows from Cloud» в меню прошивки скачивает с серверов
  Microsoft среду восстановления Windows, а та собирает заводскую Windows с
  драйверами. Запуск ручной, файлы пользователя стираются.
- **Apple macOS Recovery через интернет** [6]. Mac на процессорах Intel сами
  переходят к восстановлению через интернет, если встроенная среда
  восстановления не запускается. Прошивка скачивает её с сервера Apple, а
  переустановку macOS дальше запускает пользователь.
- **Windows Quick Machine Recovery** [7]. После повторных сбоев загрузки
  Windows сама выходит в сеть из среды восстановления WinRE и применяет
  исправление из Windows Update, но только для массовых сбоев, для которых
  Microsoft его опубликовала. Механизм живёт в WinRE на том же диске и без неё
  не работает.

Ближе всего к OSreboot по устройству Dell BIOSConnect: при повреждённой
системе он скачивает служебную ОС по HTTPS в память. Но все эти решения
восстанавливают только систему своего производителя и со своих серверов (HP
позволяет свой сервер, но только для Windows), а Quick Machine Recovery не
переживает стирания диска вместе с WinRE.

### 2.2. Системы для дата-центров

Переустановку ОС по сети в дата-центрах автоматизировали давно:

- **MAAS** (Canonical) [1] переустанавливает ОС по сети, а с версии 3.5 умеет
  развёртывание в память: система работает целиком в RAM, на диск ничего не
  пишется. Нужны BMC или другой драйвер питания и свой DHCP.
- **OpenStack Ironic** [2] загружает ramdisk, который скачивает образ и пишет
  его на локальный диск; на одну установку уходит два цикла включения. Нужны
  BMC и инфраструктура OpenStack.

Обе системы рассчитаны на BMC и на свою сеть, в которой работает DHCP-сервер
загрузки. Научные работы ускоряют подготовку таких машин. M2 [8] (2018)
загружает узлы через iPXE с сетевых дисков iSCSI вместо копирования образа.
Подготовка узла занимает около 5 минут, больше 3 из них — инициализация
прошивки. Это примерно втрое быстрее Foreman и Ironic, которые проходят её
дважды.

### 2.3. Образы дисков и обновления с откатом

Открытые инструменты вроде Clonezilla [9] снимают и разливают образы дисков
по сети, в том числе на много машин сразу (multicast). Но запускает их
человек: они отвечают на вопрос «как восстановить», но не «когда».

Системы с A/B-разделами защищают от неудачного обновления. Новая версия
ставится во вторую копию системы, и если она не загрузится, загрузчик
возвращается к старой; в systemd-boot для этого есть счётчик неудачных
загрузок [10]. Но все копии и загрузчик лежат на одном диске, и его стирание
уносит их все.

Отсюда для OSreboot два урока. Счётчик неудачных загрузок — готовый способ
запускать восстановление автоматически (раздел 5). А спасательная система
должна жить там, куда поломка не дотянется: в OSreboot это iPXE на основном
разделе EFI и среда восстановления на сервере.

Ни одно из найденных решений не закрывает все столбцы сразу:

- решения производителей восстанавливают только свою систему и обычно со
  своих серверов;
- системы для дата-центров требуют BMC и своей сети с DHCP;
- открытые инструменты для образов запускает человек;
- системы с откатом не переживают стирания диска.

Опубликованных замеров простоя при самовосстановлении одной машины найти не
удалось. Ближайшая цифра получена на кластере и для другой задачи: около
5 минут на подготовку узла у M2 [8].

Эту нишу и занимает OSreboot. Он открыт и работает на обычном компьютере без
BMC, восстанавливает свою систему с образа из интернета и измеряет простой
внешним сервером. Его слабое место — запуск: пока восстановление начинает
команда затирания, а не обнаруженная поломка.

## 3. Как устроен OSreboot

### 3.1. Компоненты

| Компонент | Где работает | Что делает |
|---|---|---|
| Сервер (`server/`) | VPS, за nginx | Принимает heartbeat и отчёты об этапах, считает простой, показывает страницу состояния, раздаёт файлы восстановления |
| Клиент (`client/`) | Тестовая система и среда восстановления | Скрипт на POSIX shell и curl: heartbeat раз в секунду и отчёты об этапах |
| Тестовая система (`0-test-system/`) | Разделы `osreboot-esp` и `osreboot-root` | Arch Linux, собранный mkosi: systemd-boot, единый образ ядра (UKI), heartbeat, обратный SSH-туннель и команда `osreboot-wipe` (`1-wipe/`) |
| iPXE (`2-ipxe/`) | Основной системный раздел EFI, который затирание не трогает | Сетевой загрузчик с HTTPS и встроенным сценарием; его запускает systemd-boot по записи по умолчанию, которую ставит `osreboot-wipe` |
| Среда восстановления (`3-recovery/`) | Оперативная память | UKI на 132 МБ: скачивает, проверяет и записывает образы, ставит BootNext и перезагружает машину |

### 3.2. Цепочка восстановления

```
osreboot-wipe --apply (в тестовой системе)
  → запись systemd-boot по умолчанию = osreboot-ipxe.conf
  → стоп heartbeat → этап wipe → этап netboot
  → затирание первых 64 MiB обоих тестовых разделов → сброс машины
прошивка UEFI → первая запись BootOrder: systemd-boot основного раздела EFI
systemd-boot → запись по умолчанию → iPXE
iPXE → DHCP → DNS (повторы, затем 1.1.1.1 и 8.8.8.8); при ошибке заново через 10 с
     → HTTPS: boot.ipxe → osreboot-recovery.efi (UKI, работает из памяти)
среда восстановления → этапы recovery → partition → download → verify
                     → write → bootloader → reboot
прошивка UEFI → по BootNext загружает восстановленную тестовую систему
тестовая система → osreboot-netboot-off убирает запись iPXE по умолчанию
                 → первый heartbeat с новым boot ID → сервер закрывает простой
```

Демонстрация начинается с команды `osreboot-wipe --apply` в тестовой системе.
Сначала она проверяет, что первая запись BootOrder запускает systemd-boot с
основного раздела EFI и что там есть запись iPXE, и делает эту запись
записью по умолчанию (`LoaderEntryDefault`). Затем останавливает heartbeat, сообщает
серверу этапы `wipe` и `netboot`, затирает начало обоих тестовых разделов и
сбрасывает машину без штатного выключения. Так выглядит «система уничтожена»:
при следующей загрузке на разделах нет ни загрузчика, ни файловой системы.

Прошивка загружает первую запись BootOrder — systemd-boot основной системы, а
он запускает iPXE. Запись по умолчанию хранится в NVRAM и остаётся до конца
восстановления, поэтому после отключения питания на любом шаге машина снова
попадёт в iPXE. iPXE лежит на
основном системном разделе EFI, который затирание не трогает, и собран с
поддержкой HTTPS, корневыми сертификатами ISRG (Let's Encrypt) как
единственными доверенными и встроенным сценарием. Сценарий получает адрес по
DHCP, разрешает имя сервера, по HTTPS загружает `boot.ipxe`, а тот — среду
восстановления. Если какой-то шаг не удался, например нет кабеля или сервер
не отвечает, iPXE показывает ошибку и через 10 секунд начинает с DHCP заново,
сколько бы это ни длилось.

Среда восстановления — Arch Linux, собранный mkosi в один UKI, который целиком
работает в памяти. Её сервис находит тестовые разделы по меткам, скачивает
сжатые zstd образы и `SHA256SUMS` в память, проверяет контрольные суммы,
записывает образы, читает их обратно и сверяет ещё раз, расширяет корневую
файловую систему, ставит BootNext на восстановленную систему, сохраняет туда
свой журнал и перезагружает машину. Каждый шаг он сообщает серверу как этап,
но от отчётов восстановление не зависит.

Восстановленная система снова шлёт heartbeat. Новый boot ID в нём закрывает
простой, и сервер дописывает строку в `server/data/outages.csv`: начало, конец и
время каждого этапа.

### 3.3. Как измеряется простой

Сервер — один процесс Node.js без базы данных. Машина шлёт heartbeat раз в
секунду. Если их нет дольше `HEARTBEAT_TIMEOUT_MS` (3 с), сервер считает
машину недоступной. Началом простоя служит последний heartbeat перед ним,
концом — первый после него, и оба момента берутся по часам сервера. Поэтому
таймаут влияет только на то, когда простой станет виден, а не на его
длительность, и сбитые часы самой машины замер не портят.

Перезагрузка быстрее таймаута тоже считается простоем: её выдаёт смена boot ID
в heartbeat. Отчёт об этапе открывает простой, если его ещё нет, потому что
скрипт затирания отчитывается раньше, чем система упадёт. По времени этапов
простой раскладывается на части: затирание, сетевая загрузка, скачивание,
проверка, запись, перезагрузка.

В терминах теории распределённых систем это детектор отказов на heartbeat с
фиксированным таймаутом [11]. Он может принять задержку сети за
отказ. Адаптивные детекторы вроде φ accrual [12] подстраивают
порог под наблюдаемые задержки, но для замера длительности простоя одной
машины фиксированного порога хватает: ложная тревога лишь откроет простой,
который закроется следующим heartbeat.

Страница `/` показывает по каждому устройству heartbeat, таймер простоя,
текущий этап с прогрессом, прошлые простои и скачивания файлов. Обновления
приходят через server-sent events. Страница `/probe` проверяет доступ к
серверу из текущей сети: время ответа, скорость скачивания и POST-запросы.

### 3.4. Предохранители

Среда восстановления пишет на диск, поэтому она осторожна:

- пишет только в разделы с метками `osreboot-esp` и `osreboot-root` и только
  если каждая метка встречается один раз, оба раздела лежат на одном диске,
  тип раздела подходит, файловая система — vfat или ext4 (или её нет), размер
  не больше 4 GiB и 128 GiB, а сам раздел не смонтирован;
- проверяет, что сама работает из памяти, а не с диска;
- сверяет SHA-256 образов до записи, а после записи читает разделы обратно и
  сверяет ещё раз;
- при любой ошибке перестаёт писать, сообщает этап `failed` с причиной,
  оставляет вход на консоли и по SSH для разбора, а через 20 минут
  перезагружает машину в её основную систему;
- ждёт, пока сеть не вернётся: запрос к серверу, на который нет ответа,
  повторяется каждые 10 с, а прерванное скачивание (меньше 1 КиБ/с в течение
  минуты) продолжается с места обрыва; повреждённые образы скачиваются заново,
  до трёх раз;
- перед перезагрузкой после ошибки убирает запись iPXE по умолчанию
  (`osreboot-netboot-off`), иначе машина возвращалась бы к той же ошибке.

Вся цепочка не должна оставлять машину там, куда без человека не добраться.
Обрыв сети её только приостанавливает, а после отключения питания она
начинается заново с iPXE, пока восстановленная система не запустится и не
уберёт запись iPXE по умолчанию.

Что происходит при обрыве сети и отключении питания:

| Шаг | Выдернули кабель | Отключили питание |
|---|---|---|
| `osreboot-wipe` до затирания | отчёты о `wipe` и `netboot` теряются, затирание идёт дальше | запись iPXE уже стоит: после включения машина восстанавливает систему |
| прошивка, systemd-boot | — | после включения снова iPXE |
| iPXE: DHCP, DNS, загрузка UKI | ошибка, через 10 с всё заново, пока кабель не вернут | после включения снова iPXE |
| среда восстановления: скачивание | ждёт сеть, затем докачивает с места обрыва | после включения снова iPXE, скачивание с начала |
| проверка, запись, BootNext | сеть не нужна, теряются только отчёты | разделы записаны не до конца: после включения снова iPXE и запись заново |
| загрузка восстановленной системы | heartbeat ждёт сеть, простой закрывается, когда она вернётся | если BootNext уже израсходован, снова iPXE и восстановление заново |
| восстановленная система работает | heartbeat ждёт сеть | запись iPXE уже убрана: машина загружает основную систему |

`osreboot-wipe` ничего не затирает, пока не убедится, что после сброса
запустится iPXE.

В образах нет секретов, поэтому их можно раздавать публично. Токен устройства
зашифрован TPM машины (`systemd-creds`) и расшифровывается только на ней.

### 3.5. Что пришлось решать по ходу

- **Прошивка ноутбука не загружает по адресу, записанному на самой машине.** В
  её настройках есть только PXE. Загрузочную запись UEFI HTTP Boot с адресом
  сервера, созданную вручную, прошивка удаляет при следующем включении, ещё до
  загрузки, и сервер не получает ни одного запроса. Так же она поступает,
  если вписать адрес в её собственную запись HTTP Boot: удаляет её и создаёт
  заново с пустым адресом. Записи SysPrep и OsRecovery из спецификации UEFI
  она принимает, но по сети ничего не загружает. HTTPS она не умеет вовсе:
  модуля TLS в прошивке нет. Остаётся её собственная запись HTTP Boot с пустым
  адресом: адрес она ждёт от DHCP-сервера сети (опции 60 и 67). Дома его можно
  настроить на роутере, но в чужой сети его никто не выдаст, поэтому этот путь
  не проверялся. Так iPXE и оказался на диске, в основном разделе EFI.
- **Сборка iPXE `snponly` не видела сетевую карту** при запуске с диска. Она
  работает через сетевой драйвер прошивки, а полная сборка `ipxe.efi` — со
  своими драйверами, и именно она заработала.
- **Домашний роутер отвечал на первые DNS-запросы ошибкой**, и iPXE сообщал
  «DNS name does not exist». Сценарий повторяет запрос три раза, а затем
  пробует публичные DNS-серверы.
- **Прошивка занимала чужие загрузочные записи.** Одноразовая загрузка iPXE
  через BootNext дважды загрузила вместо него прежнюю систему с тестового
  раздела. Найдя переписанный тестовый раздел EFI, прошивка Insyde создаёт для
  него свою запись «EFI Hard Drive» и оба раза записала её под номером записи,
  которой не было в BootOrder: сначала «OSreboot test», затем «OSreboot iPXE»
  (Boot0005). После этого `efibootmgr -n 0005` загружал тестовый раздел.
  Теперь iPXE запускает systemd-boot основной системы по своей записи
  (`LoaderEntryDefault`), а от прошивки нужна только первая запись BootOrder,
  которую она ни разу не трогала. На тестовых разделах лежит образ с
  SSH-туннелем, чтобы машина оставалась доступной, даже если прошивка загрузит
  их сама.
- **Ошибка сетевой загрузки оставляла машину в консоли iPXE**, куда удалённо
  не попасть, а возврат из iPXE в systemd-boot открыл бы его меню без
  таймаута. Поэтому при ошибке iPXE начинает заново, а среда восстановления
  после сбоя ждёт 20 минут и перезагружает машину.
- **Одноразовая запись не переживала отключения питания.** systemd-boot
  стирает её, как только запускает iPXE, поэтому после отключения питания
  или перезагрузки из iPXE машина попадала в основную систему с уже стёртой
  тестовой. Теперь `osreboot-wipe` ставит запись по умолчанию, а убирает её
  восстановленная система.
- **После сброса старая SSH-сессия часами висит на сервере** и держит
  TCP-порт обратного туннеля. Поэтому туннель идёт через Unix-сокет, который
  следующее подключение заменяет (`StreamLocalBindUnlink`).

## 5. Ограничения

- **iPXE должен пережить уничтожение системы.** Он лежит в основном разделе
  EFI, который затирание не трогает. Если стереть весь диск, цепочка
  оборвётся. Останется только сетевая загрузка силами прошивки (UEFI HTTP Boot
  или PXE), а прошивка этого ноутбука берёт адрес загрузки только у
  DHCP-сервера сети (раздел 3.5). Встроить iPXE в саму прошивку можно только
  перепрошивкой микросхемы BIOS. От неё отказались: неудачная запись выводит
  ноутбук из строя, и без программатора его уже не поднять.
- **Восстановление запускает команда затирания, а не сама поломка.**
  `osreboot-wipe` заранее делает запись iPXE записью по умолчанию. Если система сломается
  сама, прошивка об этом не узнает. Нужен счётчик неудачных загрузок, как
  Automatic Boot Assessment в systemd-boot [10] или порог
  неудачных загрузок в Dell SupportAssist OS Recovery [3]. Отличить
  поломку от отключения питания — отдельная задача.
- **Прошивка непредсказуема.** Она сама создаёт и переписывает загрузочные
  записи. Поэтому iPXE запускает systemd-boot, а от прошивки нужно одно:
  загрузить первую запись BootOrder. На машине без systemd-boot нужен другой
  загрузчик, которому ОС задаёт запись по умолчанию, или запись прошивки, если
  прошивка такие записи не трогает.
- **Цепочка не подписана.** Secure Boot выключен. iPXE проверяет сервер по
  сертификату HTTPS, а среда восстановления проверяет образы по `SHA256SUMS` с
  того же сервера. Значит, тот, кто управляет сервером, управляет и
  восстановлением. С Secure Boot нужно подписывать iPXE и UKI, а образы — ещё
  и отдельным ключом, как это делает HP Sure Recover с подписанным манифестом
  [4].
- **Нет удалённого питания.** Если машина зависнет до сетевой загрузки,
  например в меню прошивки, без человека, IP-KVM или умной розетки её не
  поднять.
- **Мало замеров.** Четыре прогона на ноутбуке, из них два полных, и прогоны в
  виртуальной машине показывают, что цепочка работает и даёт близкие цифры, но
  статистикой не являются.

## 6. Выводы

Обычный ноутбук без BMC и без помощника в локальной сети может сам
восстановить уничтоженную систему через интернет. Для этого хватает прошивки
UEFI, iPXE с HTTPS, среды восстановления в памяти и VPS с образами. На
ноутбуке полный простой, от затирания до первого heartbeat восстановленной
системы, занял 164 и 166 с в двух прогонах, а работа среды восстановления —
от 54 до 56 с в четырёх. Внутри среды восстановления время уходит в основном
на скачивание, а его скорость ограничивало 100-мегабитное подключение
ноутбука. Но во всём простое больше половины занимают две загрузки машины:
прошивка, загрузчики и ядра.

Обзор показал, что части задачи давно решены по отдельности. Сетевую
переустановку умеют системы для дата-центров, восстановление из облака —
прошивки и ОС Dell, HP, Lenovo, Apple и Microsoft, откат неудачного
обновления — системы с A/B-разделами. Открытого решения для обычного
компьютера без BMC, которое восстанавливает стёртую систему через интернет и
измеряет простой извне, найти не удалось.

Следующие шаги:

1. серия прогонов (`extra/results/run-series.sh`) с разбивкой простоя по этапам;
2. более быстрое восстановление: гигабитное подключение вместо 100 Мбит/с,
   меньший UKI среды восстановления, скачивание без пауз опроса, переход в
   восстановленную систему через kexec;
3. автоматический запуск восстановления по счётчику неудачных загрузок;
4. проверка UEFI HTTP Boot на прошивках других машин и с адресом от DHCP
   (опции 60 и 67), чтобы обойтись без iPXE на диске;
5. подпись цепочки для Secure Boot.

## Приложение. Как запустить

### Запуск

Нужен Node.js 24 или новее:

```sh
cp server/config/devices.example.json server/config/devices.json   # добавьте хеши токенов, см. «Устройства»
npm ci
npm run build && npm start
```

Сервер слушает только `127.0.0.1:8090`. Из интернета к нему обращаются через
обратный прокси, см. «Развёртывание». Файлы для раздачи кладутся в `server/files/`.

Для разработки:

```sh
npm run dev      # собирает страницы и запускает сервер с перезапуском при изменениях
npm run verify   # проверка типов, тесты и сборка
```

Настройки берутся из переменных окружения; пути по умолчанию считаются от `server/`:

| Переменная | По умолчанию |
|---|---|
| `PORT` | `8090` |
| `HOST` | `127.0.0.1` |
| `HEARTBEAT_TIMEOUT_MS` | `3000` |
| `DATA_DIR` | `data` |
| `FILES_DIR` | `files` |
| `DEVICES_FILE` | `config/devices.json` |

### Устройства

У каждого устройства свой токен, а сервер хранит только его хеш SHA-256:

```sh
openssl rand -hex 32 | tr -d '\n' > laptop.token
sha256sum laptop.token   # значение для tokenSha256 в server/config/devices.json
```

На устройстве токен хранится зашифрованным с помощью TPM этого устройства,
поэтому в самом образе системы секретов нет:

```sh
systemd-creds encrypt -T --name=osreboot-token laptop.token /etc/credstore.encrypted/osreboot-token
```

### API

| Метод | Путь | Запрос и ответ |
|---|---|---|
| POST | `/api/heartbeat` | `{"boot": "<boot_id>"}`, ответ 204 |
| POST | `/api/progress` | `{"stage": "download", "percent": 42, "message": "server.raw.zst"}`, ответ 204 |
| GET | `/api/state` | текущее состояние в JSON |
| GET | `/api/events` | то же состояние в виде server-sent events |
| GET, HEAD | `/files/<path>` | файлы из `files/`, поддерживаются диапазоны байтов |
| GET | `/health` | `ok` |

POST-запросам нужен заголовок `Authorization: Bearer <токен устройства>`.
Имя этапа должно соответствовать `[a-z0-9][a-z0-9_-]{0,31}`. Для `wipe`,
`netboot`, `recovery`, `partition`, `download`, `verify`, `write`,
`bootloader` и `reboot` на странице состояния есть понятные названия;
остальные имена показываются как есть.

### Клиент

`client/osreboot-client` — скрипт на POSIX shell, которому нужен только curl:

```sh
osreboot-client heartbeat
osreboot-client stage download 42 "server.raw.zst"
```

Адрес сервера он берёт из `OSREBOOT_URL`, а токен — из `OSREBOOT_TOKEN_FILE`
или из systemd credential `osreboot-token`.
`client/osreboot-heartbeat.service` запускает heartbeat как сервис.

Любой heartbeat завершает простой, поэтому скрипт в работающей системе
останавливает сервис heartbeat, прежде чем сообщить этап.

### Тестовая система

`0-test-system/` собирает с помощью mkosi 25 или новее систему, которую демонстрация
затирает и восстанавливает: Arch Linux с systemd-boot и единым образом ядра
(unified kernel image), DHCP на проводных сетевых картах, SSH только по
ключам, сервис heartbeat и обратный SSH-туннель к серверу (см.
[SSH в тестовую систему](#ssh-в-тестовую-систему)). На консоли tty1 вход под
root выполняется автоматически. Система ставится на два раздела целевого
диска с метками `osreboot-esp` (системный раздел EFI не меньше 512 MiB) и
`osreboot-root`.

Локальные настройки в git не хранятся. `0-test-system/mkosi.local.conf` добавляет
дополнительное дерево файлов:

```ini
[Content]
ExtraTrees=mkosi.local.extra
```

В `0-test-system/mkosi.local.extra/` лежат
`etc/systemd/system/osreboot-heartbeat.service.d/server.conf` с переменной
`OSREBOOT_URL`, `root/.ssh/authorized_keys` и, при необходимости,
`etc/credstore.encrypted/osreboot-token` — токен устройства, зашифрованный
TPM машины; расшифровать его может только этот TPM.

```sh
mkosi -C 0-test-system build   # сначала собирает собственное дерево инструментов
```

В образе нет секретов в открытом виде, поэтому для восстановления его можно
раздавать публично.
`0-test-system/write-test-system.sh` запускается на целевой машине из её основной
системы. Он записывает образы обоих разделов и считывает их обратно для
сверки, расширяет корневую файловую систему, шифрует токен устройства с
помощью TPM машины и кладёт его в тестовую систему, а также добавляет
загрузочную запись в прошивку UEFI, не меняя порядок загрузки:

```sh
sudo bash write-test-system.sh DIR           # только проверки
sudo bash write-test-system.sh DIR --apply
```

В `DIR` лежат `osreboot-test.esp.raw.zst`, `osreboot-test.root-x86-64.raw.zst`,
`SHA256SUMS` несжатых образов и, при необходимости, `osreboot.token`.
mkosi создаёт только несжатые образы `.raw`:

```sh
cd 0-test-system/mkosi.output
zstd -T0 -12 osreboot-test.esp.raw osreboot-test.root-x86-64.raw
sha256sum osreboot-test.esp.raw osreboot-test.root-x86-64.raw > SHA256SUMS
```

Ещё в тестовой системе есть `osreboot-wipe` из `1-wipe/` — шаг демонстрации
«система уничтожена». Запущенный под root в тестовой системе, он проверяет, что первая
запись BootOrder запускает systemd-boot с основного раздела EFI и что там есть
запись `osreboot-ipxe.conf` вместе с её программой, делает эту запись
записью по умолчанию (`bootctl set-default`), останавливает heartbeat, сообщает этапы
`wipe` и `netboot`, затирает первые 64 MiB обоих разделов и сбрасывает
машину. Запись по умолчанию переживает отключение питания. Её убирает
`osreboot-netboot-off.service`, когда запустится восстановленная система:

```sh
osreboot-wipe           # только проверки и план
osreboot-wipe --apply
```

### Загрузка по сети

iPXE лежит на основном системном разделе EFI, который затирание не трогает, а
запускает его systemd-boot основной системы по записи по умолчанию.
`2-ipxe/build.sh` собирает `2-ipxe/out/ipxe.efi` — iPXE на зафиксированном коммите
с поддержкой HTTPS, корневыми сертификатами ISRG от Let's Encrypt в качестве
единственных доверенных и встроенным скриптом `2-ipxe/osreboot.ipxe`. Этот скрипт
получает адрес по DHCP, разрешает имя сервера (повторяет попытки, затем
пробует DNS-серверы 1.1.1.1 и 8.8.8.8) и загружает по цепочке (`chain`)
`https://HOST/files/boot.ipxe`. При любой ошибке он ждёт 10 секунд (Ctrl-B
открывает консоль iPXE) и начинает заново с DHCP, а не возвращается в меню
загрузчика.

`2-ipxe/install-ipxe.sh` запускается из основной системы целевой машины. Он
кладёт `ipxe.efi` в `/EFI/osreboot/ipxe.efi` на её разделе EFI и добавляет
запись systemd-boot `osreboot-ipxe.conf`, проверив сначала, что первая запись
BootOrder запускает systemd-boot с этого раздела. Запись по умолчанию в меню
не меняется: если бы с новой записью она поменялась, скрипт удаляет запись и
останавливается.

```sh
bash 2-ipxe/build.sh osreboot.example.org
sudo bash 2-ipxe/install-ipxe.sh 2-ipxe/out/ipxe.efi           # только проверки
sudo bash 2-ipxe/install-ipxe.sh 2-ipxe/out/ipxe.efi --apply
sudo systemctl reboot --boot-loader-entry=osreboot-ipxe.conf   # восстановление один раз
```

Это запись загрузчика, а не прошивки: прошивка Insyde демо-ноутбука, найдя
переписанный тестовый раздел EFI, создаёт для него свою запись и дважды
записала её под номером записи, которой не было в BootOrder.
`2-ipxe/boot.ipxe` кладётся в `files/` на сервере и запускает среду
восстановления из того же каталога. Если это не удалось, он возвращает
управление встроенному скрипту, и тот перезагружает машину.

Встроенная в прошивку загрузка по HTTP (HTTP Boot) не может заменить iPXE на
демо-ноутбуке: его прошивка Insyde удаляет загрузочные записи с адресом
сервера при следующем включении, не обратившись к нему, а адрес для своей
записи HTTP Boot берёт только у DHCP-сервера сети (раздел 3.5).

### Среда восстановления

`3-recovery/` собирает `osreboot-recovery.efi` — целую систему в едином образе
ядра, которая работает из памяти. Её сервис `osreboot-recovery` находит
разделы с метками `osreboot-esp` и `osreboot-root`, скачивает оба образа и
`SHA256SUMS` из `files/` на сервере, проверяет их, записывает, считывает
обратно, расширяет корневую файловую систему, ставит BootNext на тестовую
систему, сохраняет свой журнал в `/var/log/osreboot/` тестовой системы и
перезагружает машину. Он сообщает этапы `recovery`, `partition`, `download`,
`verify`, `write`, `bootloader` и `reboot` или `failed` с причиной;
восстановление от этих отчётов не зависит. Без сети он ждёт: запросы к
серверу повторяются каждые 10 с, а прерванное скачивание продолжается с места
обрыва (`curl -C -`). После ошибки он оставляет вход на консоли и по SSH,
убирает запись iPXE по умолчанию и через 20 минут перезагружает машину в её
основную систему; `systemctl stop osreboot-fallback-reboot.timer` оставляет
её в среде восстановления. Он отказывается работать с
разделом, если у того другой тип, файловая система не vfat и не ext4 или
размер больше 4 GiB (ESP) или 128 GiB (root), и ничего не пишет на диск за
пределами этих двух разделов.

Локальные настройки среда восстановления берёт у тестовой системы.
`3-recovery/mkosi.local.conf`:

```ini
[Content]
ExtraTrees=../0-test-system/mkosi.local.extra
ExtraTrees=mkosi.local.extra
```

`3-recovery/mkosi.local.extra/etc/systemd/system/osreboot-recovery.service.d/server.conf`
задаёт `OSREBOOT_URL`. В виртуальной машине, где нет TPM целевой машины, токен
можно передать как systemd credential `osreboot-token`.

```sh
mkosi -C 3-recovery build
```

После этого в `files/` на сервере лежат `boot.ipxe`, `osreboot-recovery.efi`,
оба образа `.raw.zst` и `SHA256SUMS`.

### SSH в тестовую систему

У восстановленной системы нет публичного адреса, поэтому
`osreboot-tunnel.service` открывает обратный SSH-туннель к серверу. Он входит
под пользователем `osreboot-tunnel` и пробрасывает Unix-сокет
`/var/lib/osreboot-tunnel/sock/ssh.sock` на сервере к своему sshd; nginx на
сервере публикует этот сокет на порту 2221:

```sh
ssh -p 2221 root@osreboot.example.org
```

Туннель — это сокет, а не TCP-порт, потому что система перед затиранием была
сброшена, не закрыв своё соединение. sshd на сервере держит такую сессию
часами, и TCP-порт остался бы занят, а сокет заменяется при следующем
подключении (`StreamLocalBindUnlink`). Восстановленная система доступна через
несколько секунд после загрузки.

`osreboot-ssh-host-key.service` до запуска sshd кладёт на место постоянный
ключ хоста, поэтому после каждого восстановления клиенты видят один и тот же
ключ хоста. Оба закрытых ключа — это credentials, зашифрованные TPM машины,
как и токен устройства. Без них туннель повторяет попытки каждые 10 с, а sshd
генерирует новый ключ хоста.
`make-ssh-credentials.sh` создаёт оба ключа на целевой машине из её основной
системы:

```sh
sudo bash make-ssh-credentials.sh DIR
```

Он записывает в `DIR` файлы `osreboot-tunnel-key.cred` и
`osreboot-ssh-host-key.cred` вместе с их `.pub`; закрытые ключи в открытом
виде никогда не покидают память. Локальные настройки в
`0-test-system/mkosi.local.extra/`:

- `etc/credstore.encrypted/osreboot-tunnel-key` и
  `etc/credstore.encrypted/osreboot-ssh-host-key` — два файла `.cred`;
- `etc/systemd/system/osreboot-tunnel.service.d/server.conf`, который задаёт
  `OSREBOOT_TUNNEL=osreboot-tunnel@SERVER`;
- `etc/ssh/ssh_known_hosts` — ключ хоста сервера: `SERVER ssh-ed25519 AAAA…`.

Среда восстановления использует те же файлы и `0-test-system/mkosi.extra`, поэтому
во время работы открывает тот же туннель.

На сервере под root, имея под рукой `osreboot-tunnel-key.pub`:

```sh
useradd --system --user-group --home-dir /var/lib/osreboot-tunnel \
	--no-create-home --shell /usr/sbin/nologin osreboot-tunnel
install -d -m 0755 /var/lib/osreboot-tunnel /var/lib/osreboot-tunnel/.ssh
install -d -m 0755 -o osreboot-tunnel -g osreboot-tunnel /var/lib/osreboot-tunnel/sock
echo "restrict,port-forwarding,command=\"/usr/sbin/nologin\" $(cat osreboot-tunnel-key.pub)" \
	>/var/lib/osreboot-tunnel/.ssh/authorized_keys
install -m 0644 server/deploy/sshd-osreboot-tunnel.conf /etc/ssh/sshd_config.d/90-osreboot-tunnel.conf
sshd -t && systemctl reload ssh
```

`server/deploy/nginx-osreboot-ssh.conf` подключается в контекст `stream {}` nginx.
Пользователь `osreboot-tunnel` может пробросить только этот сокет и ничего
больше: ни shell, ни TCP-портов. Клиенту достаточно один раз добавить ключ
хоста тестовой системы в доверенные:

```sh
echo "[osreboot.example.org]:2221 $(cut -d' ' -f1,2 osreboot-ssh-host-key.pub)" >>~/.ssh/known_hosts
```

### Серия прогонов и статистика

`extra/results/run-series.sh` повторяет демонстрацию для серии замеров; ему нужны
ssh, curl и jq. Перед каждым прогоном он проверяет, что устройство в сети и
что `osreboot-wipe` проходит свои проверки, и печатает скорость проводного
подключения: при 100 Мбит/с скачивание не может идти быстрее 11 MiB/с. Затем
запускает `osreboot-wipe --apply` через SSH-туннель и ждёт, пока
восстановленная система снова пришлёт heartbeat. Если прогон не закончился за
`TIMEOUT_S` (900 с), серия останавливается: неудачное восстановление скрипт
повторно не затирает.

```sh
OSREBOOT_URL=https://osreboot.example.org OSREBOOT_SSH=root@osreboot.example.org \
	extra/results/run-series.sh 10
```

`server/dist/outage-stats.js` сводит `server/data/outages.csv` в таблицу: строка на каждый
прогон со средой восстановления, время между этапами, а внизу минимум, медиана
и максимум каждого столбца. Прогон, который не дошёл до перезагрузки (ошибка
или обрыв скачивания), остаётся в таблице с пометкой в последнем столбце, но в
минимум, медиану и максимум не входит: его простой длится, пока кто-нибудь не
загрузит тестовую систему.

```sh
node server/dist/outage-stats.js server/data/outages.csv
node server/dist/outage-stats.js extra/results/outages-2026-10-23.csv   # замеры раздела 4
```

`server/dist/downtime-figure.js` рисует шкалу времени одного прогона, как на рисунке 2.
Этапы он берёт из `outages.csv`, а границы внутри сетевой загрузки — из списка
скачиваний. Этот список есть только в ответе `/api/state`: в `state.json` на
диске сервер хранит одни устройства. Сервер помнит только 10 последних
скачиваний, это около двух прогонов, поэтому `run-series.sh` сохраняет ответ
`/api/state` после каждого прогона в `SAVE_DIR` (по умолчанию
`extra/results/series-<время UTC>` в каталоге проекта). Без третьего аргумента
берётся последний полный прогон `osreboot-wipe`, а третий аргумент выбирает
прогон по началу его времени в UTC:

```sh
node server/dist/downtime-figure.js extra/results/outages-2026-10-23.csv extra/results/state-2026-10-23.json >extra/figures/downtime.svg
node server/dist/downtime-figure.js extra/results/outages-2026-10-23.csv extra/results/state-2026-10-23.json --dark >extra/figures/downtime-dark.svg
```

### Развёртывание

Сервер демонстрации работает прямо на VPS, без Docker: Node.js из `/opt/node`
запускает `server/deploy/osreboot.service` под временным пользователем (`DynamicUser`)
с ограничениями systemd. Код лежит в `/opt/osreboot` (`package.json` и `dist/`),
состояние и `outages.csv` — в `/var/lib/osreboot`, файлы для раздачи — в
`/srv/osreboot/files`, хеши токенов — в `/etc/osreboot/devices.json`. nginx
на VPS проксирует к `127.0.0.1:8090`, то есть `REMOTE_PORT` в конфигах ниже —
это 8090. Обновление сервера:

```sh
npm ci && npm run build
tar czf - -C server/dist . | ssh root@VPS 'cd /opt/osreboot && rm -rf dist.new && mkdir dist.new &&
	tar xzf - -C dist.new --no-same-owner && rm -rf dist && mv dist.new dist &&
	systemctl restart osreboot'
ssh root@VPS /opt/node/bin/node /opt/osreboot/dist/outage-stats.js /var/lib/osreboot/outages.csv
```

Конфиги в `server/deploy/`:

- `nginx-osreboot-host.conf` отдаёт страницы на собственном имени
  хоста, чтобы страница состояния открывалась в корне этого имени.
- `sshd-osreboot-tunnel.conf` и `nginx-osreboot-ssh.conf` —
  серверная часть SSH-туннеля, см.
  [SSH в тестовую систему](#ssh-в-тестовую-систему).
